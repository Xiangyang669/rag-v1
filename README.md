# rag-v1 · 三层检索 RAG

一个单机自研的检索系统：**向量、全文、知识图谱三条通路并行召回**，用 RRF（倒数排名融合）合成最终排序。参考 RAGFlow 的两条数据流设计，但技术栈全部换成轻量自研组件——不依赖任何外部服务。

```
        ┌─→ 向量检索（Chroma + bge-m3）    ─┐
query ──┼─→ 全文检索（SQLite FTS5 bm25）   ─┼─→ RRF 融合 → 输出
        └─→ 图谱检索（实体 → 关联块）      ─┘
```

## 它解决什么

单个检索通路各有盲区：

- **向量**擅长语义，但遇到精确术语（函数名、配置项）会失手
- **全文**擅长精确匹配，但换个说法就找不到
- **图谱**能回答"这个参数在哪些函数里出现过"这类**跨块聚合**问题——而前两条路本质上都是"块打分排序"，天然只会返回孤立的块

三条通路**并行**发起、融合排序。不是"一路不行再试下一路"——那会让一次查询的延迟变成三路之和。

## 关键设计取舍

每一条都写清代价——选型不是"因为它更好"，而是"我愿意付这个代价"。

| 取舍 | 选了 | 放弃了什么 |
|---|---|---|
| 融合策略 | **RRF（只看排名）** | 丢掉绝对分数：看不出第 1 名比第 2 名强多少。换来的是免疫三路量纲差异（余弦相似度 / BM25 负值 / 图谱命中数） |
| 图谱抽取 | **纯规则，零 LLM** | 只能抽结构性能抽的关系（`has_parameter` / `belongs_to`），**抽不出函数调用关系**；图谱只有一跳，答不了多跳推理 |
| 实体消解 | **规则（全限定名 + 别名表）** | 处理不了"它/该模块"这类代词指代。但技术实体的标识是确定性的，规则比 LLM 更准且可复现 |
| 排序 | **RRF 输出即最终排序** | V1 没有独立重排模块（cross-encoder 留待 V2） |
| 评估集 | **按文档结构自动生成** | 问题词面贴近原标题 → **全文路占便宜、图谱增益被系统性低估**（报告中的图谱增益应视为下界） |
| 图谱存储 | **SQLite 两张表 + 内存 NetworkX** | 不引入图数据库；遍历靠内存，规模受单机内存限制 |

## 架构

### 数据流 A · 入库（离线）

```
技术文档 → loader → elements（Element 中间表示 → 分块）→ tokenizer
                      ├─→ 向量支线：embedding → Chroma
                      ├─→ 全文支线：分词 → SQLite FTS5
                      └─→ 图谱支线：结构抽取 → SQLite nodes/edges + 内存图
```

loader / elements / tokenizer 是三条路**共用**的前置，只在写入时分开——否则同一个块在三路里边界不一致，融合时对不上。

`loader` 把文档拆成有序的 **Element**（正文段 / 表格 / 后续还会有图片），
`elements` 再切块。表格因此是**独立 chunk**，不走正文那条「按段落贪心、超限
按字符硬切」的路径——大表按「表头 + 若干行」切，**每块都重复表头**，宁可让
单行超限也不切断它。每个 chunk 还带来源元数据（文档名 / 页码 / 位置 / 原图引用），
由 `FtsStore.meta_of` 回源、经 `create_app(meta_lookup=...)` 暴露到 API。

### 数据流 B · 在线检索

三条召回通路由 LangGraph Supervisor 并行扇出，汇入 RRF 融合节点；单路故障自动降级（整体仍返回结果，`degraded` 字段如实告知哪一路缺席）。

## 快速开始

```bash
pip install -r requirements.txt
py -m pytest                              # 151 个测试
```

真实索引需要 embedding API（SiliconFlow `BAAI/bge-m3`）。把 key 放进项目根的 `.env`：

```
SILICONFLOW_API_KEY=sk-...
```

然后：

```python
from pathlib import Path
from ragv1.config import CORPUS_DIR, INDEX_DIR
from ragv1.ingest.build import build_corpus

print(build_corpus(CORPUS_DIR, INDEX_DIR))   # 返回写入的块数
```

## 目录

```
ragv1/
├── ingest/        loader（版面分析→Element）· 表格解析 · 分块 · 结构抽取 · 入库编排
├── store/         向量（Chroma）· 全文（FTS5）· 图谱（SQLite + NetworkX）
├── retrieve/      三路检索器 + 独立开关
├── fusion/        RRF 融合
├── orchestration/ LangGraph Supervisor（并行调度 + 降级 + 埋点）
├── evaluation/    A/B/C/D 四类问题自动生成 · 分层指标 harness · 验收报告
├── api/           FastAPI 端点
└── observability.py  Langfuse 埋点（无 key 时 no-op）
```

## 已知限制

- **评估集有系统性偏差**：自动生成的问题词面贴近标题，全文路占便宜、图谱增益被低估
- **图谱只做一跳**，且不含函数调用关系（需解析代码，留待后续）
- **无重排**：融合输出即最终排序
- **语料目录在 `config.py` 里写死**为开发时使用的路径
- **无鉴权、无部署**（V1 定位是本地验证版）
