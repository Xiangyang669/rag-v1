# rag-v1 · 三层检索 RAG

一个单机自研的检索系统：**向量、全文、知识图谱三条通路并行召回**，用 RRF（倒数排名融合）合成最终排序。参考 RAGFlow 的两条数据流设计，但技术栈全部换成轻量自研组件——不依赖任何外部服务。

```
        ┌─→ 向量检索（Chroma + bge-m3）    ─┐
query ──┼─→ 全文检索（SQLite FTS5 bm25）   ─┼─→ RRF 融合 → 输出
        └─→ 图谱检索（实体 → 关联块）      ─┘
```

## 它解决什么

单个检索通路各有盲区：

- **向量**擅长语义，但遇到精确术语（函数名、配置项）会失手
- **全文**擅长精确匹配，但换个说法就找不到
- **图谱**能回答"这个参数在哪些函数里出现过"这类**跨块聚合**问题——而前两条路本质上都是"块打分排序"，天然只会返回孤立的块

三条通路**并行**发起、融合排序。不是"一路不行再试下一路"——那会让一次查询的延迟变成三路之和。

## 关键设计取舍

每一条都写清代价——选型不是"因为它更好"，而是"我愿意付这个代价"。

| 取舍 | 选了 | 放弃了什么 |
|---|---|---|
| 融合策略 | **RRF（只看排名）** | 丢掉绝对分数：看不出第 1 名比第 2 名强多少。换来的是免疫三路量纲差异（余弦相似度 / BM25 负值 / 图谱命中数） |
| 图谱抽取 | **纯规则，零 LLM** | 只能抽结构性能抽的关系（`has_parameter` / `belongs_to` / `mentioned_in`），**抽不出函数调用关系**；图谱只有一跳，答不了多跳推理。**⚠️ `belongs_to` 与 `mentioned_in` 是 M2.5 才真正写进代码的——此前 README 在这一行声称的 `belongs_to` 在代码里并不存在**（见「V2」节） |
| 实体消解 | **规则（全限定名 + 别名表）** | 处理不了"它/该模块"这类代词指代。但技术实体的标识是确定性的，规则比 LLM 更准且可复现 |
| 排序 | **RRF 输出即最终排序** | V1 没有独立重排模块。**已做对照实验，见 [`RERANK_AB.md`](RERANK_AB.md)：naive 重排在本评估集上是负收益（recall@5 −0.149）** |
| 评估集 | **按文档结构自动生成** | 旧的 A/C/D 三类问题与图谱索引**用同一套 heading 结构**——A 类问题直接由 `heading_path[-1]` 生成，图谱路匹配的正是标题，所以图谱在 A 类拿到 recall@5 = **1.000**。这不是「偏向」，是**回声**：评估集与图谱路共享同一份数据结构，它的增益被系统性高估（见 `evaluation/report.py` §4.1 / `ACCEPTANCE.md`） |
| 图谱存储 | **SQLite 两张表 + 内存 NetworkX** | 不引入图数据库；遍历靠内存，规模受单机内存限制 |

## V2：中文评估与图谱修复（M2 + M2.5）

V1 之后做了两件事：M2 在中文评估集上做加权融合的调参，M2.5 修图谱路在中文语料上的空转。结论里既有通过，也有被推翻的旧结论。

### M2 · 静态权重调优：判据 1 未通过

在 `zh_dev.jsonl` 上调静态权重、在 `zh_test.jsonl` 上报数（18 条可回答题，`unanswerable` 已排除）：

- 加权融合 recall@5 = **0.889**，最强单路（全文）= **0.917** → **判据 1 未通过**。
- 但当时等权融合 recall@5 = **0.972**，是赢的——**这个「赢」后来被 M2.5 推翻了**（见下）。

### M2.5 · 图谱路在中文语料上完全空转的修复

M2 收官时实测：**图谱路对 22 条中文测试题返回 0 条块**——完全空转。两个独立根因：

1. **关系只有 `has_parameter` 一种，且只在标题长成 `name(params)` 签名时才产出**。中文标题是 `(1)如何检查模型可用性` 这类白话 → 永不解析 → 中文索引 `edges` 表 0 行。
2. **`_contains_phrase` 用 `f" {n} " in f" {h} "` 做词边界**。英文按空格分词是对的（也是防 `url` 匹配 `curling` 的机制），但中文连写无空格 → 连用户把标题一字不差说出来都匹配不到。

修复（提交 `d8375b5`、`7b570fe`、`b53beb9`、`ee69c10`）：

- 章节层级落成 `belongs_to` 边（`extract.py` 里本有 `parent` 变量，但只用于命名限定，从不产出层级关系）。
- 从正文抽 `identifier` 实体（`MULTIPLE_DATA_TO_BASE64`、`config.json`、反引号术语）+ `mentioned_in` 边。此前实体**只来自标题**，正文一概不看。
- 修中文短语匹配：ASCII 走原有词边界路径，CJK 改取连续 CJK 段（≥ `MIN_CJK_RUN=4`）做子串匹配——编号前缀 `(1)`/`2.3` 不含 CJK，天然被跳过。
- **计划外发现并修复**：`GraphStore.__init__` 只建空的内存图，把边读进内存的唯一入口是 `build()`，而生产装配路径 `api/server.py::_open` 从不调它。所以那 4587 条边在生产路径上根本读不到，`neighbors()` 对全部 1188 个 section 返回 `[]`。**这是 V1 就有的缺陷**——既有测试全都先手搓 `build(chunks)` 再断言 `neighbors()`，所以真实链路里它是空的这件事从没被测出来。

### M2.5 实测

| 判据 | 结果 |
|---|---|
| 图路不再空转 | ✅ 0/22 → **20/22 返回非空** |
| CJK bug 修复 | ✅ 标题逐字出现在查询里，False → True |
| 一跳真的存在 | ✅ 题 2/8 的正确答案**只能**经一跳到达；图路 recall@10 0.194 → 0.306 |
| B 的收益可归因 | ✅ 题 15 完全来自 `MULTIPLE_DATA_TO_BASE64` 节点 |
| 零回归 | ✅ **324 个测试**（3 条 smoke 跳过） |

**归因拆开写，不要合并成一个数**：标识符节点（任务 21）**单独**把图路从 0 拉到 18/22；中文标题匹配（任务 22）再加 2 条；磁盘加载修复（任务 24）对 **recall@5 毫无贡献**（0.194 → 0.194），只把 **recall@10** 从 0.194 提到 0.306（增量全部来自第 9、10 名）。

### 一跳修复后，融合数字变了——并推翻了 M2 的一个结论

一跳修复后重跑融合表（`zh_test.jsonl`，18 条可回答题）：

| 行 | recall@5 | recall@10 | MRR |
|---|---|---|---|
| vector | 0.778 | 0.889 | 0.508 |
| fulltext（最强单路） | **0.917** | 0.944 | 0.789 |
| graph | 0.194 | 0.306 | 0.197 |
| fused_eq（等权） | 0.889 | 0.972 | 0.685 |
| fused_static（加权） | 0.861 | 0.889 | 0.569 |

**判据 1（融合 ≥ 最强单路）在所有方案下均未通过**：加权 0.861、等权 0.889，都低于全文路的 0.917。

**为什么会变**：M2 时等权融合 recall@5 = **0.972 > 0.917（赢的）**，那是因为**图路当时完全空转**——它返回空，对融合而言等于不存在，当时的「三路融合」实际是**两路融合**，所以能赢。M2.5 让图路真的工作之后，它开始往融合结果里投票，而它很弱（recall@5 0.194），于是**把融合拖了下来**。

**所以 M2 那个「等权赢」是图路空转的副产品，不是融合策略的胜利。** 加权 RRF 本来的目的正是给弱路降权——方向对，但 dev 集调出的权重没做到（0.861 比等权还差）。

**一条必须同时写的限定**：这些都是 **18 条**可回答题上的差异，0.861 与 0.917 之间只差一道题左右，**落在噪声里**。所以正确的表述是「**目前无法判定融合是否胜过最强单路**」，而不是「融合输了」。

> ⚠️ **英文评估集未随 M2.5 重建索引**：M2.5 改了抽取逻辑，但 `.indexes/kb`（英文）仍是 V1 基线、没重建。所以 `ACCEPTANCE.md` / `RERANK_AB.md` 里的英文 A/B/C/D 数字描述的是**修复前**的图谱路，跨 M2.5 不可比，不要当成当前代码在英文上的表现。这两个文件是历史记录，未改动。

## 架构

### 数据流 A · 入库（离线）

```
文档（.md / .pdf）
   │
   ├─ loader ── 版面分析 → 有序 Element 流
   │     ├─ 正文段 ──────────────────────────┐
   │     ├─ 表格   → Markdown 表              │
   │     └─ 图片   → OCR 通道 ┐               │
   │                多模态通道┴→ 分流合并      │
   │                                          ↓
   └─────────────────────────── elements（Element → 分块）→ tokenizer
                                      ├─→ 向量支线：embedding → Chroma
                                      ├─→ 全文支线：分词 → SQLite FTS5
                                      └─→ 图谱支线：结构抽取 → SQLite nodes/edges + 内存图
```

loader / elements / tokenizer 是三条路**共用**的前置，只在写入时分开——否则同一个块在三路里边界不一致，融合时对不上。

`loader` 把文档拆成有序的 **Element**（正文段 / 表格 / 图片），`elements` 再切块。

- **表格**因此独立成 chunk，不走正文那条「按段落贪心、超限按字符硬切」的路径——
  大表按「表头 + 若干行」切，**每块都重复表头**，宁可让单行超限也不切断它。
- **图片**走两条互补通道：OCR 拿图上的**字**（扫描件、报错截图），多模态拿**视觉
  内容**（流程图走向、图表趋势）。两者兼有时**都产出**，按 `order` 排回阅读顺序。
  文字为主的图只走 OCR，不重复花一次多模态调用。
- 每个 chunk 都带来源元数据（文档名 / 页码 / 阅读序号 / 位置 / 原图引用），由
  `FtsStore.meta_of` 回源、经 `create_app(meta_lookup=...)` 暴露到 API。

**任何解析失败都落降级码，不静默丢弃**（14 个码，见 `ingest/degrade.py`）。

### 数据流 B · 在线检索

三条召回通路由 LangGraph Supervisor 并行扇出，汇入 RRF 融合节点；单路故障自动降级（整体仍返回结果，`degraded` 字段如实告知哪一路缺席）。

## 快速开始

```bash
pip install -r requirements.txt
py -m pytest                              # 324 个测试（默认跳过需要真实引擎的 smoke）
py -m pytest -m smoke -v -s               # 真跑 OCR / 多模态，打印实测输出
```

真实索引需要 embedding API（SiliconFlow `BAAI/bge-m3`）。把 key 放进项目根的 `.env`（也支持上层 `practice/.env`）：

```
SILICONFLOW_API_KEY=sk-...
```

**① 建索引**（走真 embedding；语料路径默认取 `config.CORPUS_DIR`）：

```bash
py scripts/build_index.py                 # 落盘 .indexes/kb/，打印块数 / 耗时 / API 调用次数
py scripts/build_index.py --with-images   # 带图片双通道（取图 40-68s/张，很慢）
```

**② 起服务**（本地）：

```bash
py -m ragv1.api.server                    # http://127.0.0.1:8000/docs
```

**③ 起服务**（Docker，同一份镜像服务任意索引）：

```bash
docker compose up --build -d              # http://127.0.0.1:8000
```

> ⚠️ 两个部署坑，都是实测踩出来的：
> ① compose 里挂索引的卷**必须可写**——Chroma 的 `PersistentClient` **即使只读查询也要写 sqlite**，挂 `:ro` 会抛 `attempt to write a readonly database`。
> ② 容器里要**显式把 Langfuse key 留空**——否则压测会夹带外部埋点的网络延迟，数字不可复现。

## 部署与实测性能

**测法**：`docker compose up`（Docker Desktop / WSL2，Windows 10），脚本 `scripts/bench.py`
发 300 个请求（10 条真实 query 轮转），并发 10、预热 10。

| 场景 | P50 | P95 | P99 | QPS |
|---|---|---|---|---|
| **全三路**（含 1 次 embedding 往返） | 346 ms | **556 ms** | 783 ms | 26.6 |
| **纯本地**（关向量路，0 次外部调用） | 224 ms | 276 ms | 308 ms | 43.8 |
| 纯本地 · 并发 1 | 26 ms | 56 ms | — | 28.8 |

**四个面试要的数字**：

| 数字 | 值 |
|---|---|
| **P95 延迟** | **556 ms**（全三路，并发 10）。拆开看：**纯本地检索只要 26 ms**（并发 1），其余全是 embedding API 的一次网络往返 |
| **QPS** | **~44**（天花板。并发 10 与 20 都是 43-44，**吞吐不再涨、延迟线性变长**） |
| **一次查询的外部调用** | **1 次 embedding + 0 次 LLM** |
| **一次查询的 token** | **8.1 token**（10 条 query 共 81；`scripts/bench.py --token-probe` 实测） |

> 💡 **「一次链路几次 LLM 调用」的答案是 0** —— rag-v1 是**检索内核**，不调 LLM；一次查询只在
> 向量路把 query 编码成向量（1 次 embedding 往返），融合 / 全文 / 图谱全在本机。
> **把大模型留给回答层，这是分层取舍。** 带 LLM 的完整链路在另一个项目。

### 已定位的瓶颈：库层的全局锁，把吞吐钉死在 ~44 QPS

并发 1 → 10 → 20 时，**QPS 停在 43-44 不动，P50 却从 26 ms 涨到 224 ms 再到 454 ms**
——**吞吐不涨、延迟随并发线性变长**，是存在全局串行点的典型特征。

根因在 `store/fts_store.py:65` 与 `store/graph_store.py:31`：两者各持**一条 sqlite 连接 +
一把 `threading.Lock`**（`check_same_thread=False` 的标准写法），**每个查询都要过这把锁**
→ 全文路与图谱路的查询被完全串行化。

方向（未做）：单连接换连接池（每线程一条），或对只读查询放开锁。
**在 107 篇 / 2050 块的规模下它不是瓶颈，但它是这套架构上生产要迈的第一道坎。**

## 已知限制

- **评估集是「回声」而不是「偏向」图谱路**：旧的 A/C/D 三类问题与图谱索引用同一套 heading 结构——A 类问题直接由 `heading_path[-1]` 生成，图谱路匹配的正是标题，所以图谱在 A 类拿到 recall@5 = 1.000。它的增益被系统性高估，不是低估。
- **图路功能正常但非主力**：中文评估集上图路 recall@5 = **0.194**，远低于全文 0.917 / 向量 0.778。它作为第三条召回通道参与融合，没有调权重去粉饰它。
- **图谱只做一跳，且一跳只能到父级与子级、到不了兄弟**（树结构上一跳无法横向）；也不含函数调用关系（需解析代码，留待后续）。
- **中文短语匹配的边界**：只有用户说出标题、或标题里的连续中文片段（≥4 字）才命中；完全换措辞描述同一章节仍不命中——不做分词/同义词/相似度。
- **标识符抽取有噪声**：反引号判据在真实文档上等于「作者放进反引号的任何东西都抽」，实测带进纯数字、单字母、中文白话词；全大写判据会带进 `HTTPS`/`README` 这类通用词（占 `mentioned_in` 边的 2.6%）。
- **中文评估集是 AI 起草、经两轮审查，不是人工标注**：44 条（dev/test 各 22 条，各含 4 条 `unanswerable`，可回答题各 18 条）。已知有 6 条偏弱（例如 2 条是/否极性问、1 条与语料措辞接近、2 条语义近重复）。
- **多轮题的 `history` 未纳入检索评估**：所有行同等受损，不代表真实多轮表现。
- **判据 1 没有最终答案**：唯一一次测量是 18 条题上的，0.861 与 0.917 只差一道题左右、落在噪声里；评估集**没有扩容**。
- **M2.5 的改动没有被任何为它设计的评估类别覆盖**：原计划要加的 `structural` 类（「X 在哪些文档里被提到过」「这一章有哪些子章节」这类只有结构路答得对的题）**没有写**。M2.5 的验证全部来自直接度量，不是来自评估集。
- **无重排**：融合输出即最终排序。**已实测对照**（[`RERANK_AB.md`](RERANK_AB.md)）：加 naive cross-encoder 重排后 recall@5 **−0.149**、MRR **−0.126**——只在语义型（B）问题上变好。根因是 reranker 打的是**单块**相关性，与「答案是一组块」的 C/D 类不匹配
- **版面分析是自研轻量版**：用 bbox 聚类，不是 ML 布局模型；**双栏/多栏排版可能切歪**。接口留成可替换的，见 `ingest/layout.py`
- **图片只转成文本参与检索**，不进向量库做以图搜图
- **图片解析依赖网络**：语料里的图是远程 URL，实测本机到 `raw.githubusercontent.com` 每次取图要 40-68 秒且常失败——取不到就落 `image_fetch_failed` 并继续，不会中断入库
- **扫描版 PDF 的 OCR 质量取决于渲染分辨率**，没有做倾斜校正/去噪
- **语料目录在 `config.py` 里写死**为开发时使用的路径
- **无鉴权**：`/search` 裸奔，没有任何鉴权/限流（V1 定位是本地验证版）
- **检索层无 LLM**：本服务只做检索，不生成回答；拒答/引用溯源也不在这一层
- **并发天花板 ~44 QPS**：库层的全局锁所致，见「部署与实测性能」末节
