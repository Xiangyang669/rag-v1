# rag-v2 · M2.5 设计补充：让图谱路名副其实

> 日期：2026-10-09 · 分支：`feat/v2-llm-layer` · 父 spec：[`2026-10-09-rag-v2-llm-layer-design.md`](2026-10-09-rag-v2-llm-layer-design.md)
>
> 修订：初版把 C（查询侧匹配）当作"可选的放宽、有精度风险"并砍掉；实测证明它是**中文下的匹配 bug**，已收回该定性，见 §1.2。

## 1. 为什么有这份补充

M2 收官时量出一个计划外的事实：**图谱路在中文语料上完全空转。**

实测（只读、无 API 成本）：

```
英文 kb:    nodes 916  = {section: 914, function: 1, parameter: 1}   edges 1
中文 kb_zh: nodes 1188 = {section: 1188}                            edges 0

22 条 zh_test 题走 GraphRetriever：返回非空的 0 / 22
```

**两个独立的根因**，必须都修——只修一个，图路仍然不可用。

### 1.1 根因一 · 关系只有 `has_parameter`，层级从不落成边

`ingest/extract.py`：

1. **实体只来自 `heading_path`**，正文一概不看（docstring 明说「正文里出现某个词不代表文档在定义它」）。
2. **关系只在标题长成 `name(params)` 签名、且名字与每个参数都匹配标识符正则时才产出**（`extract.py:89-109`），而且唯一被构造的 kind 是 `has_parameter`。
3. 中文标题是 `(1)如何检查模型服务器可用性` 这类白话 → 签名永不解析 → **0 条边**。

后果：`GraphStore.neighbors()`（`graph_store.py:94-101`）读的是由这些关系建出的内存图，边为空 → **「一跳邻居扩张」——README 称为图谱路独家价值的能力——在 V1 和 V2 都从未工作过**。

这同时解释了 V1 一个此前无法解释的数字：`ACCEPTANCE.md` 里图路 A 类 recall@5 = **1.000**，看着最强。但 A 类问题是由 `heading_path[-1]` 生成的（`qa_gen.py:50-58`）——**图路匹配标题，评估集由标题生成，两边是同一份数据结构**。V1 README §4.1 称之为「评估集结构偏向图谱路」；实情比「偏向」更强：是**回声**。

### 1.2 根因二 · 短语匹配靠空格做词边界，而中文没有空格（**bug**）

`retrieve/graph_retriever.py:30-37`：

```python
def _contains_phrase(haystack: str, needle: str) -> bool:
    if not needle:
        return False
    return f" {needle} " in f" {haystack} "      # 两侧补空格做词边界
```

这个写法对**英文**是对的——它正是防止 `url` 匹配上 `curling` 的机制。但**中文按字连写、没有词间空格**，于是：

```
真实标题: '(1)如何检查模型可用性问题'
查询:     '(1)如何检查模型可用性问题是怎么实现的？'    ← 标题逐字包含在查询里
_normalize(标题) = '1 如何检查模型可用性问题'
_contains_phrase(查询, 标题) = False
GraphRetriever._matched_entities(查询) = set()

对照（英文）：_contains_phrase('how does browser work', 'browser') = True
```

**所以图路不是在中文上「命中率低」，而是结构性地不可能命中任何中文标题**——包括用户把标题一字不差说出来。这是缺陷，不是设计边界。V1 从未发现，是因为它的基准语料是英文。

### 1.3 顺带发现的一处文档不实

`README.md:67` 宣称抽取器产出 `has_parameter / belongs_to` 两种关系。**`belongs_to` 在整个代码库里不存在**（改动 A 之后才会真实存在）。这不是设计取舍，是文档写了代码没做的事实。**必须更正**（见 §8）。

## 2. 范围

### 做

- **A · 把章节层级写成真正的边**（产出 README 已经宣称的 `belongs_to`）
- **B · 从正文抽取非标题实体**（`identifier` 类型节点 + `mentioned_in` 边）
- **C · 修中文的短语匹配**（§1.2 的 bug）

### 不做（明确出局）

- 任何 LLM 参与的抽取（本项目图谱抽取的既有契约是**纯规则、零 LLM**，不破）
- 引入图数据库（既有取舍：SQLite 三表 + 内存 NetworkX）
- 语义关系抽取（谁调用谁、谁替代谁）——README 从未宣称，保持诚实
- 修复「图谱路是否能在本语料上赢」——见 §7 判据 5 的诚实边界

## 3. 改动 A · 章节层级边

**现状**：`extract.py:112-124` 的 `_chunk_graph` 遍历 `chunk.heading_path` 时**已经维护了一个 `parent` 变量**，但只把它用于同名实体的命名限定（`f"{parent}.{raw_name}"`），**从不产出任何层级关系**。

**改成**：对 `heading_path` 中每一对相邻的 (父, 子)，产出一条

```python
Relation(src=child_canonical, dst=parent_canonical, kind="belongs_to")
```

方向是「子 belongs_to 父」，与 README 用词一致。

**效果**：`neighbors(section)` 返回该 section 的父级与全部子级 → 一跳扩张第一次真的有东西可扩。边数从 1/0 涨到与节点数同量级（层级树的边数 = 节点数 − 根数）。

**契约**：
- 顶层标题（`parent is None`）不产边，不抛错。
- 重复的 (src, dst, kind) 去重——既有 `seen_relations` 集合已保证。
- 确定性：输出仍然排序（`extract()` 末尾已排序）。
- **`identifier` 节点不得成为任何 `belongs_to` 的 src 或 dst**（它不在 `_STRUCTURAL_KINDS` 里，天然满足，但要有测试钉住）。

## 4. 改动 B · 正文非标题实体

**现状**：实体只来自 `heading_path`。FastGPT 中文文档里大量出现的 `MULTIPLE_DATA_TO_BASE64`、`config.json`、`docker-compose.yml`、`projects/code-sandbox/src/env.ts` 一个都没进图。

**改成**：新增一个纯规则抽取器，从 `chunk.text` 抽三类**高精度**标识符：

| 形态 | 例子 | 判据 |
|---|---|---|
| 全大写下划线常量 | `MULTIPLE_DATA_TO_BASE64`、`CHAT_MAX_QPM` | `[A-Z][A-Z0-9_]{3,}` 且（含下划线 或 长度 ≥5）——排除 `AND`/`OK`/`FAQ` |
| 文件名 / 路径 | `config.json`、`docker-compose.yml`、`a/b/c.ts` | 显式扩展名白名单（见下），形态为 `[\w./-]+\.(ext)` |
| 反引号包裹的术语 | `` `appId` ``、`` `$text` `` | 成对反引号内的非空内容 |

扩展名白名单（模块级常量，可加不可减式地扩充）：

```
json yml yaml toml ini conf env md txt sh ps1 py js ts tsx jsx go java rs sql log
```

形态 `[\w./-]+\.(白名单之一)`，且 `.` 前至少有 1 个字符、扩展名后不接词字符（避免 `config.json5x` 之类误配）。

产出：

```python
Entity(canonical=<标识符原样>, kind="identifier", aliases=(<原样>, <小写>))
Relation(src=<标识符>, dst=<所在 section>, kind="mentioned_in")   # section 取 heading_path 的叶子
```

并**进入 posting list**（`entities_of_chunk` 要让标识符出现在它所在的块上）——否则抽出来也回不到原文。

**为什么 B 不改检索器就能生效**：`GraphRetriever._matched_entities`（`graph_retriever.py:45-55`）遍历的是 `GraphStore.aliases()`，对**所有节点**（不只 section）做匹配。所以用户 query 里出现 `MULTIPLE_DATA_TO_BASE64` 时，新节点自动命中，并立刻触发改动 A 带来的一跳扩张。

**契约与边界**：
- `identifier` **不进** `_STRUCTURAL_KINDS`——它不能成为父标题，否则会污染层级命名。
- **大小写：在 `Entity.aliases` 里同时登记原样与小写两种形态。** `_normalize` 内部会 `.lower()`，把两种形态都登记成别名，则检索器一行都不用动，`MULTIPLE_DATA_TO_BASE64` 与 `multiple_data_to_base64` 都能命中同一节点。canonical 保持原样（大小写是标识符的身份）。
- 同形标识符在不同文档出现 → 归并为一个节点（既有 `merged` 逻辑），posting list 自然聚合跨文档出现位置——这正好是图路该答的那类问题。
- 噪声控制：宁可少抽，不可把普通中文词抽成实体。三条判据都要求**形态特征**，不做裸词抽取。

## 5. 改动 C · 修中文的短语匹配

**性质**：这是 §1.2 那个 bug 的修复，**不是"放宽匹配以提升命中率"**。目标是让「用户说出了标题」这件事**至少能被匹配到**；不是让任意自然语言都能命中。

**改成**：`_contains_phrase` 分两条路径，按别名**是否含 CJK** 分流。

```
ASCII 别名  → 保持现有 ` needle ` 空格词边界逻辑（它是对的，且是防 url/curling 的机制）
CJK 别名    → 不用空格边界；从规范化标题里取「连续 CJK 段」，
              只要某一段长度 ≥ MIN_CJK_RUN（初值 4）且出现在规范化 query 里 → 命中
```

**为什么用「连续 CJK 段」而不是整条标题的子串**：标题普遍带编号前缀，如 `(2)前端错误` → 规范化后是 `2 前端错误`。整条子串匹配会被 `2 ` 这个前缀挡掉；而提取 CJK 段得到 `前端错误`，4 个字，能正常命中。编号前缀不含 CJK，天然被这条规则跳过。

**精度守门**：
- `MIN_CJK_RUN` 下限挡住「介绍」「说明」这类 2–3 字的短标题在全库泛匹配。
- **不改 section 的排名逻辑**：命中后仍走现有的「按命中数降序、块 ID 升序」，不引入新权重。
- 阈值取值放 `config.py`，在 **dev 集**上定；`MIN_CJK_RUN` 的搜索范围与最终值要记进验收报告。

**明确不做**：不做中文分词后的词袋匹配、不做同义词扩展、不引入任何相似度模型。这条路径必须保持"可解释、可复现、零 LLM"，与项目既有取舍一致。

## 6. 测试策略

沿用 TDD 与「先看着它失败」。

**必须有的边界测试：**

- 顶层标题不产 `belongs_to` 边，不抛错
- 三层标题链产出两条 `belongs_to`，方向为「子 → 父」
- `identifier` 不出现在任何 `belongs_to` 的 src 或 dst 里
- 全大写常量判据：`MULTIPLE_DATA_TO_BASE64` 抽出；`AND` / `OK` / `FAQ` **不**抽出
- 文件名判据：`config.json` 抽出；中文句号不抽
- 反引号判据：成对才抽；落单的反引号不抽、不抛
- **大小写**：`MULTIPLE_DATA_TO_BASE64` 与 `multiple_data_to_base64` 都能命中同一节点
- 标识符确实进入 posting list：`chunks_of(identifier)` 返回它所在的块
- **C 的核心回归（§1.2 的原样复现）**：查询 = 标题逐字 + 后续中文，`_matched_entities` 必须非空。**这条要先写成失败测试**，它当前是红的。
- **C 的编号前缀**：标题 `(2)前端错误` 应能被「前端错误怎么排查」命中
- **C 的精度守门**：`MIN_CJK_RUN` 以下的短标题不得触发命中
- **C 不破坏英文**：`url` 仍不匹配 `curling`（现有英文词边界行为逐字节不变）
- 确定性：同一输入两次运行，实体与关系逐字节一致
- **回归**：不含标识符、单层标题的文档，抽取结果与改动前逐字节一致

## 7. 验收判据

1. **图路不再空转**：在 `zh_test.jsonl` 上，图路返回非空的题数从 **0/22** 显著上升（给出实测数字），且 recall@5 > 0。
2. **C 的 bug 修复可复现**：§1.2 那段「标题逐字出现在查询里」的复现用例，从 False 变为命中。
3. **一跳真的存在**：`neighbors(<某个 section>)` 返回非空；构造一条只有一跳能答对的情况并测住。
4. **B 的收益可归因**：至少一条评估集题的图路命中，可追溯到新抽出的 identifier 节点（而不是章节标题匹配）。
5. **零回归**：全部既有测试全绿。
6. **诚实边界**：若图路在该语料上**仍然不是主力**，照实写「功能正常但非主力」，**不得**为了让它好看去调权重或改判据。

## 8. 对既有文档与评估的影响

- **`README.md:67` 必须更正**：`belongs_to` 在改动 A 之后才真实存在；`has_parameter` 只在签名标题上产出。取舍表要写清两种关系各自的产出条件与局限。
- **新增一条已知限制**：改动 C 让「用户说出标题」可被匹配，但**用户用完全不同的措辞描述同一章节时，图路仍返回空**（不做分词/同义词/相似度，见 §5 明确不做）。这条必须写进 README 的已知限制，不能含糊。
- **英文结构性评估集（A/B/C/D）的新旧可比性会被打破**：`qa_gen.py` 的 C/D 两类是用 `graph.chunks_of` / `graph.aliases()` **从图里生成**的，改动 A/B 会改变图，因而也改变这两类的问题与答案集。**这不是回归，是评估集的输入变了。** M2.5 落地后必须重新生成并重新基线化，并在验收报告里注明「英文结构性集在 M2.5 前后不可直接比较」。真正的回归护栏是**测试**，不是那套评估数字。
- **中文人工评估集不受影响**（它是人工写的，不是从图生成的）。

## 9. 已知局限

- 改动 C 只覆盖「用户说出了标题或标题里的连续中文片段」。**完全换措辞描述章节仍不命中**——这是有意保留的边界（§5 明确不做分词/同义词/相似度），因为它正是精度与可解释性的取舍点。
- 标识符抽取是规则驱动的，**漏抽**比错抽更可能（如 `camelCase` 配置项不在三条判据里）。宁可漏，不可错。
- 层级边只表达「章节归属」，**不表达语义关系**。README 也从来没宣称过，保持诚实。
